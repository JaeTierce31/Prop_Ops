# J3S CRM Intake 001B Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement J3S-CRM-INTAKE-001A as an executable intake-domain spine in `JaeTierce31/Prop_Ops`, proving migrations, policy oracles, append-only epistemics, tenant isolation, deterministic routing, and INT-001–INT-020 before any intake renderer is added.

**Architecture:** Extend the existing hardened Property Ops branch with a bounded `src/domain/intake` module plus migration `008_crm_intake_001b.sql`. Keep qualification and routing pure/deterministic, keep AI extraction advisory/append-only, and emit proposed commands/outbox events rather than mutating CRM opportunity state directly. Preserve existing server-derived authority and RLS conventions from migrations 001–007.

**Tech Stack:** TypeScript 5.8, Vitest 4, PostgreSQL/Neon, TanStack Start, Zod, existing server authz/RLS/outbox conventions.

**Spec:** J3S-CRM-INTAKE-001 / J3S-CRM-INTAKE-001A from the approved conversation contract; branch base `prop-ops-authz-harden-001@fbeef17078ff3206332fcb83abba829559e458b5`.

## Global Constraints

- No renderer or frontend intake flow until INT-001–INT-020 pass.
- Published intake/policy versions are immutable.
- UNKNOWN is distinct from false/zero/empty.
- Qualification and routing remain separate deterministic machines.
- AI inference cannot satisfy qualification-critical fields without confirmation.
- Public submissions create provisional identities only.
- Tenant authority is server-derived; request payload tenant IDs never establish scope.
- Answers, provenance, consent, evidence lineage, qualification results, and routing decisions are append-only/superseding.
- Canonical CRM effects occur only through proposed commands independently authorized by the receiving domain.
- All mutating operations use idempotency plus optimistic revision checks.
- State mutation and outbox insertion are atomic.

## Review Focus

- Unknown/non-applicable/conflicting values must not collapse into score zero or satisfy required guards.
- Duplicate idempotency keys with changed payloads must fail rather than replay a stale receipt.
- AI-confirmed flags must be derived from authorized confirmation events, not trusted from public request bodies.
- Policy version changes must never reinterpret historical qualification/routing results in place.
- Cross-tenant exact identity matches and evidence lookups must remain impossible even when identifiers collide.
